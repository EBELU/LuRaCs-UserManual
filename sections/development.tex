The core of the application is built on a number of singleton classes that manage the global state of the program. These are reachable from anywhere in the program.

\paragraph{Settings}
The settings contain modifiable parameters that affect the running of the program. It is divided in the the following parts. Settings can also be used for communication within the program as when a setting is changed using the \texttt{update\_setting} function a signal is emitted from \texttt{Settings} with the group of the setting, name of the setting and the new value.
\begin{itemize}
    \item \textbf{Appearance} contain simple settings mostly controlling appearance of the GUI and preferences for data import.
    \item \textbf{Paths} contain file and system paths to resources and stored data.
    \item \textbf{Temp} contain values that are reset upon shutdown.
    \item \textbf{State} saves mostly last used values for convenience and is capable of saving and loading complex data types like dequeues.
    \item \textbf{Advanced} contains advanced options that most users rarely need to change.
\end{itemize}
\paragraph{RunManager} 
The RunManager handles connecting and sampling instruments. It owns its own thread running an async event loop, this to avoid instrument sampling being affected by events in the GUI thread and vice versa. Threadsafe communications are handled using Qt signals. The RunManager also owns the \textbf{SpectrogramManager} which tracks spectrogram and manages spectrogram ROIs.
\paragraph{ScriptEngine} 
The ScriptEngine is responsible for converting text commands into actions. Like the RunManager it owns it own thread and communications are made using Qt signals. Available commands are described in the section on the CLI. 
\paragraph{Log} The Log exports a reference to the python logger "Application".
\paragraph{IOManager} The IOManager provides functions for import and export of various files and manages indexes of internally stored file for the Data Store.
\paragraph{SpectrumManager} The SpectrumManager is one of the most critical parts of the application. It owns all spectra, both from files and devices. Modifications of spectra are handles through it. It also owns the following components.
\begin{itemize}
    \item \textbf{NuclideLibrary} contains loaded nuclide data and some functions for interacting with it.
    \item \textbf{ROIManager} handles spectrum ROIs and updates peak fits.
    \item \textbf{GenericInsturmentLibrary} contains generic instruments based on instrument models that can be used to store characterisc data and be used as basis for UniqueInstruments.
    \item \textbf{UniqueInsturmentLibrary} contains unique instruments that can be assigned to spectra. They differ from GenericInstruments in that they store information unique to each device like energy calibration.
\end{itemize}

The core also contains the helper class \textbf{Calculator} that is designed to easily assign a CPU intensive task to a separate thread and signal back the result using a Qt signals.

\subsection{Wrapping Detectors}
The implementation of detectors is written be extensible and make it easy to implement new instruments. This is facilitated though inheritance from an abstract class \texttt{DeviceWrapper}. This wrapping hides the individual device implementations and LuRaCs only interact through this wrapper interface. Creating a subclass from \texttt{DeviceWrapper} automatically registers the new wrapper for use as a detector connection. 

\subsection{Algorithms}
\subsubsection{Peak Fitting}
Peak fitting are based in ROIs in which a peak is assumed to be. Each ROI can contain one peak but ROIs can merge so several peaks can share the same background estimation. One a ROI is defined the fitting process is as follows.
\begin{enumerate}
    \item Determine a number of channels starting at the ROI and counting inwards on which to base the background.
    \item A polynomial is fitted using the edge channels and their corresponding counts.
    \item The polynomial is evaluated for every channel in the ROI or the merged ROI region and the result subtracted from the respective channels.
    \item One or the sum of several Gauassian functions are fitted to the remainder.
    \item Peak characteristics are extracted from the fitted paramters.
\end{enumerate}

The uncertainties of the peak fitting is calculated as follows. Firstly, the counts in channel \textit{i}, $N_i$ is assumed to follow Poisson distribution, thus $\sigma_i = \sqrt{N_i}$. The uncertainty of each channel is used as weights for the polynomial fit.

\subsubsection{Simple map tracks (.geojson)}
Spectrograms are the primary way to store GPS position data these are however not directly compatible with any other software without custom scripts. A spectrogram can be converted to the \textit{GeoJSON} format, with the loss of some information, for compatibility and easier sharing. The \textit{GeoJSON} format is generally compatible with dedicated GIS software, like \textit{QGis}, for viewing measurements outside the embedded map.

\subsection{Embedded map}
The embedded map is rendered using \textit{MapLibre GL JS}\footcite{MaplibreMaplibregljs2026} in a QWebEngine widget. The packages for MapLibre is included in the LuRaCs code and does not require any installation. MapLibre handles requesting tiles is connected to an online API it requires minimal work. Using maps offline works by using an embedded tile server run using \textit{uvicorn} and \textit{fastapi} to supply MapLibre with tiles. The embedded tile server runs on host 127.0.0.1 and port 8080. PMTiles are loaded using a fork of the \textit{pmtiles} Python package, having improved cacheing and performance, incorporated in the LuRaCs code.

The code is written so that the the Python side handles most of the logic, using only simple calls to JS for creating or updating points, etc. To minimise the overhead incurred from the \textit{Python} $\leftrightarrow$ \textit{JS}-bridge send lists as a one object and let JS iterate over it, as opposed to sending every point over the bridge.
